# 12 Child and Screen Child
- **Child**: same base functionality with layout or extra processing differences (e.g. Term Deposit account as child of customer account STDCUSAC -> STDCUSTD). New + Function Type Child + load Parent Xml; category inherited and fixed. Visit Preferences node at least once so function id there becomes the child's. No multi-level inheritance (no child of child).
  - Allowed: new data sources/columns, new + modified LOVs, modify parent block field props, new screens/tabs/sections, add/remove fields in field sets (block of existing field set fixed), new field sets, new call/launch forms (deactivate inherited), amendable changes, full summary redesign. Not allowed: delete/rename parent elements (hide instead).
  - Generates all units; SMTB_MENU.PARENT_FUNCTION set. Child main package calls parent's hooks before child hooks for each stage (parent logic reused; skip via skip handlers). `Pr_convert_child_to_master` / `Pr_convert_master_to_child` convert types whenever calling parent packages.
- **Screen Child**: from a parent OR a child; layout only, reuses parent packages + JS. Only nodes Data Blocks, Screens, Field Sets, Actions. No deletions, no new blocks/fields. Editable field props: Field Label, Field Size, Max Decimals, Default Value, Preview Value, Visible, Read Only, Calendar Text, Popup Edit Required, Uppercase Only, Input by LOV only, Not Required in XSD. New screens/field sets/tabs/sections/partitions OK. Web service + operation configurable, amendables not. Generates only screen XML, menu details, label details, XSD, screen HTML.
