# Cross-cutting cheat sheet
- **Layers**: KERNEL (product) < CLUSTER (region) < CUSTOM (bank). Each layer writes only its own hook package `<MOD>PKS_<FID>_<LAYER>` and JS `<FID>_<LAYER>.js`; never edit `_MAIN` or `_SYS.js`. Skip lower layers with `PR_SET_SKIP_<LAYER>` / `PR_SET_ACTIVATE_<LAYER>`.
- **Function id** (8 chars, chars 1-2 = module): 3rd char D detail/maintenance/online/launch/others, C call form, R report, N notification, S summary, G gateway. Purge entity id `<MOD>P<ENTITY>`.
- **Element prefixes**: blocks `BLK_` (never the table name), screens `CVS_`, tabs `TAB_` (TAB_HEADER/TAB_MAIN/TAB_FOOTER fixed), sections `SEC_`, field sets `FST_`, LOVs `LOV_`, labels `LBL_`, triggers `TRG_`, notification codes `NOTIF_<MOD>_<DESC>`. Field names: no underscores, differ from column name.
- **Release immutability**: delete/rename only in the creating release; afterwards hide (Visible) or deactivate (Active). Regenerate all units after delete/rename/reorder.
- **Data model**: exactly one master data source and one master block; PK cols/types `~`-separated; 1:N child needs one more PK col; relation written parent-first with `=` only; views only as Query/Summary data sources.
- **Category quick map**: Maintenance (generated logic, Maint Audit footer) / Transaction=Online (no generated business logic; hooks for resolve ref, unlock, product default, subsys pickup, enrich, process; SUBSYSSTAT D/U/R) / Call form (C; attach to same category; SubSys type XSD) / Launch form (view-only; manual CSTB_CALL_FORM_NODES; ACTION_CODE=EXECUTEQUERY) / Others (only type conversion; custom action codes in Fn_Main) / Report (CSTB_UI_COLUMNS + PM_* params; BIP RTF/XDO) / Dashboard (one DS/block, summary only) / Child, Screen Child / Notification / Purge / Gateway / Customer Landing Page.
- **Must-have static data to launch**: SMTB_MENU, SMTB_FUNCTION_DESCRIPTION, SMTB_ROLE_DETAIL, SMTB_FCC_FCJ_MAPPING (call forms: SMTB_MENU + SMTB_FCC_FCJ_MAPPING + CSTB_CALL_FORM_NODES). Labels live in CSTB_LABELS (maintained via ODT Label Code screen, not generated).
- **Typical dev loop**: login, set release/env (User Preferences) -> Function Generation New/Load -> design in order (DS, blocks, screens, field sets, call/launch forms, LOVs, summary, actions) -> save radxml -> Generate -> Deploy (JS/UIXML to app server paths, DB units to schema, INCs compiled) -> write hooks/release JS -> launch in FLEXCUBE and test (TCM for regression).
- **radxml file (verified 14.7, see 27)**: root RAD_FUNCTIONS; a CUSTOM-origin function needs an empty `<RAD_KERNEL/>` then `RAD_CUSTOM` (else "Non-Ext RAD xml Cannot Be Loaded"); load in a CUSTOM release with Action = Load. Generate new screens with `skills/odt-radxml/scripts/gen_radxml.py`, check with `check_radxml.py`.
- **Extending a KERNEL function (see 28)**: keep RAD_KERNEL untouched; in RAD_CUSTOM repeat a parent node only with its kernel leaf values unchanged plus the new children; every data-source PK column must be a data source field (RD-VALS-027); every new field needs a unique XSD tag (RD-VALS-60); prove no regression with `radxml_merge.py` (0 kernel values changed). Ask early whether new data must also be *processed* - kernel code is often fixed-slot.
